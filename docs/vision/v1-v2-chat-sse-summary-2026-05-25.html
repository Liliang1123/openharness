V1 / V2 Chat 与 SSE 差异梳理

当前系统的 V1 / V2 不是 URL 层面的版本切换。正式聊天入口仍然是 /api/v1/chat/{agent_id}/stream，真正决定执行引擎的是 AgentSession.loop_version。

checkout: coagents_service_release branch: release/v1.8.0 date: 2026-05-25 scope: chat stream + session events

核心结论

一句话： 调用 URL 基本不变；V2 变化在后端执行引擎、事件总线、断线恢复语义和 active stream 草稿补偿。 如果客户端只接主 POST /stream，请求仍可运行，但断线后的实时恢复能力不完整。

路由依据

后端读取 session.loop_version。值为 v2 进入新 Agent Loop，否则进入 legacy V1 执行路径。

客户端入口

主聊天仍是 POST /api/v1/chat/{agent_id}/stream。外部 legacy 接口也会转到同一个平台 chat stream。

SSE 重点

V2 需要配合 GET /api/v1/chat/sessions/{session_id}/events 和 last_event_id 做恢复。

请求方式对比

场景 V1 V2 调用方感知
主聊天流 POST /api/v1/chat/{agent_id}/stream POST /api/v1/chat/{agent_id}/stream URL 不变，按 session 的 loop_version 分流。
外部 legacy 聊天 /api/openapi/v1/external/chat/{agent_id}/stream 同一接口，内部委托到平台 chat stream URL 不变，但运行路径可能是 V2。
会话事件订阅 GET /api/v1/chat/sessions/{session_id}/events GET /api/v1/chat/sessions/{session_id}/events?last_event_id=... V2 下建议必须接入，用于断线恢复和异步事件回流。
新会话分配 无灰度命中或灰度暂停时写入 v1 灰度配置命中时写入 v2 同一调用方可能因 org/session 灰度结果不同而走不同引擎。

执行模型对比

维度 V1 V2
执行引擎 LangGraphAgentExecutor legacy stream path。 run_session_turn(...) 新 Agent Loop。
事件模型 主要围绕主 SSE 输出、DB writer、ConversationMessage 落库。 围绕 RolloutEventKind：文本增量、工具执行、产出物提交、halt、done/error。
运行态锁 有 session run lock / runtime root 兼容逻辑。 更明确地绑定 execution_id、active execution、run lock、abort signal。
中间态恢复 主流断了后主要靠 DB 最终消息和轮询。 多了 active stream 草稿快照和非持久 runtime event。
异步协作 兼容旧链路，部分结果通过 DB polling 暴露。 EventBus + BackgroundTask / rollout events 更适合多智能体、审批、产出物回流。

SSE 对比

主聊天 SSE：POST /stream

  • V1 和 V2 都会返回 start、文本 chunk、工具事件、产出物事件、done 或 error。
  • V1 的事件来自 legacy executor。
  • V2 的事件来自 RolloutEventKind，再投影成兼容的 SSE payload。
  • 主流断开后，后端使用 detached streaming 思路继续 drain，避免“看的人断了，执行就立刻死掉”。

会话事件 SSE：GET /sessions/{id}/events

  • V1：保持 DB polling，用于兼容旧 session。
  • V2：走 EventBus，先订阅实时事件，再按 last_event_id replay Redis Stream。
  • V2 可推 stream_text_delta、stream_snapshot、stream_done、stream_error。
  • 如果 cursor gap 无法补齐，会发 stream_resync_required，客户端应重拉消息列表。

V2 断线恢复流程

1. 主流开始 客户端发 POST /chat/{agent_id}/stream，拿到 session_id 和实时输出。
2. 订阅会话事件 页面同时订阅 GET /sessions/{session_id}/events。
3. 主流断开 后端继续执行；客户端实时 token 展示会中断。
4. 事件流补偿 客户端用 last_event_id 重连，收到 missed events 或 stream_snapshot。
5. 结束刷新 收到 stream_done / stream_error 或最终消息创建事件后，刷新消息列表。

客户端适配清单

能力 是否必须 说明
继续调用 POST /api/v1/chat/{agent_id}/stream 必须 主聊天入口不变，不需要改成 /api/v2。
保存 session_id 必须 后续事件订阅、断线恢复、消息刷新都依赖 session。
订阅 GET /api/v1/chat/sessions/{session_id}/events V2 强烈要求 只接主 stream 时，断线后实时展示会丢；订阅会话事件才能补偿。
维护 last_event_id V2 强烈要求 当前前端因要带 Authorization，用 fetch + ReadableStream，不是原生 EventSource，所以 cursor 要自己传。
处理 stream_snapshot / stream_text_delta 推荐 用于主流断开后恢复“正在生成中”的草稿展示。
处理 stream_resync_required 必须 表示 cursor 已无法完整 replay，应清 cursor 并重新拉取消息列表。
只依赖 POST stream 不推荐 执行不会必然丢，但断线后的实时 UI 和中间态展示不完整。

建议的外部调用方式

外部或旧客户端如果要完整支持 V2，建议把主流和会话事件流视为一组协议：主流负责本次请求的即时输出，会话事件流负责断线恢复、异步协作结果、最终消息同步。 
POST /api/v1/chat/{agent_id}/stream
Content-Type: application/json
Authorization: Bearer ...

{
  "message": "用户输入",
  "session_id": "可选；续聊时传",
  "attachments": []
}

GET /api/v1/chat/sessions/{session_id}/events?last_event_id={cursor}
Authorization: Bearer ...

需要处理的事件：
- stream_text_delta
- stream_snapshot
- stream_done
- stream_error
- stream_resync_required
- message_created
- tool_call_event
- submit_delivery
